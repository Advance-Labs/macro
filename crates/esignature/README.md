# Native eSignature

`esignature` owns immutable PDF envelopes, recipient capabilities, signing order,
consent, revocation, completion evidence, and sender account authorization. The
DSS composition root supplies PostgreSQL, PDF, SES/SMTP, and Macro authentication.
Inbound HTTP handlers only parse transport data and call the domain service.

The frontend lives in `apps/web/src/features/legal`, uses the existing service
host/authentication utilities, and registers `/app/legal` plus `/app/sign`.
The first version is account-private and supports one PDF per envelope, up to
20 recipients and 200 signature/initial/date/text fields. CLM is deferred.

## Endpoints

Authenticated management endpoints live at `/legal/envelopes`: GET lists the
latest 200 envelopes; POST creates a draft from `{title, filename,
documentBase64}`. `GET /{id}` reads metadata, `PUT /{id}` replaces the draft,
`POST /{id}/send` freezes/sends, `/resend` rotates unsigned active invitations,
`/void` closes with a reason, and `GET /{id}/document?completed=true` downloads the
completed PDF. Mutations carry the current `revision` to reject stale requests.

External recipient endpoints live at `/legal/signing`: `POST /session`,
`POST /sign`, `POST /decline`, and `GET /document?completed=true`. They accept an
`Authorization: Bearer <one-recipient capability>` header. Email URLs place that
capability in the fragment, which is not sent in server URL logs/referrers.
Only its SHA-256 is persisted. The signing response includes only that
recipient's identity and fields; it does not expose other recipient emails.

## Storage and evidence

The additive `legal_esignature_envelopes` MacroDB migration stores source PDF
bytes separately from metadata. A source fingerprint is frozen at creation.
Every write compares the previous revision atomically; all values, recipients,
and audit evidence are committed together. All-signed completion flattens field
values into the original pages, preserves document resources, embeds signature
fonts, appends a certificate, and records the final PDF fingerprint. User account
removal cascades to its envelopes; void/decline retain evidence.

Links expire 30 days after sending. Resend explicitly rotates active unsigned
links. Failed SMTP/SES delivery stays undelivered and can be retried; sending or
signing is not rolled back after its durable transition. Dates are generated by
the server. Consent, field ownership, order, replay, and terminal-state rules
are domain decisions. Identity evidence is emailed-link possession; this version
does not perform identity verification or certificate-based digital signing.

## Running and releasing

Run `cargo test -p esignature --features inbound,postgres,pdf,mail` from the root
with SQLX_OFFLINE unset. Use `SQLX_OFFLINE=true cargo check -p
 document_storage_service` for the wired service. PostgreSQL query metadata is
checked into the workspace `.sqlx` cache. Font licenses live in `assets/`.

Apply the new MacroDB migration and the cloud-storage-service SES IAM change
before deploying DSS and the frontend. Invitations use the existing verified
`macro.com` SES identity, restricted to `legal@macro.com`; local mode uses the
existing SMTP transport. The composition root selects the known production/dev
frontend URL. The local demo example supplies its own frontend origin.

`examples/local_demo.rs` binds only to loopback and uses a fixed development
credential. It exercises the same HTTP routers, PostgreSQL adapter, PDF renderer,
and SMTP transport through Mailpit. Never deploy it or use its credential against
real data. It expects Postgres at 55432, Mailpit SMTP at 11025 (set SMTP_HOST and
SMTP_PORT), and the Macro app frontend at 3003.
